## Идея

Небольшая программа-пул: пользователи вносят SOL в общий `Pool`, а их доли учитываются в `Ledger`. В ней **пять намеренно уязвимых инструкций** (`*_vuln`), в каждой ровно одна ошибка, и исправленные аналоги. Для каждой ошибки есть два теста:

1. **Эксплойт срабатывает** на уязвимой инструкции — средства украдены.
2. **Та же атака падает** на исправленной — с конкретным кодом ошибки.

> `*_vuln` инструкции написаны для обучения. Не копируйте их в боевой код.

## Уязвимости

| # | Класс ошибки | Уязвимая инструкция | Исправление | Ошибка после исправления |
|--:|--------------|---------------------|-------------|--------------------------|
| 1 | Нет проверки подписи | `withdraw_no_signer_vuln` | `owner: Signer` | `AccountNotSigner` (3010) |
| 2 | Нет проверки связи аккаунтов | `withdraw_no_has_one_vuln` | `has_one = owner` + seeds из `ledger.owner` | `ConstraintHasOne` (2001) |
| 3 | Арифметика без проверок (underflow) | `withdraw_underflow_vuln` | `checked_sub` + `InsufficientBalance` | `InsufficientBalance` (6001) |
| 4 | Нет проверки владельца аккаунта (type cosplay) | `emergency_drain_vuln` | `Account<Config>` + seeds + `has_one = admin` | `AccountOwnedByWrongProgram` (3007), `ConstraintHasOne` (2001) |
| 5 | Произвольный CPI | `deposit_via_cpi_vuln` | `Program<System>` | `InvalidProgramId` (3008) |

### Как работает каждая атака

1. **Нет подписи.** `owner` объявлен как `UncheckedAccount`. `has_one` доказывает, что ledger принадлежит этому публичному ключу, но не доказывает, что владелец *подписал* транзакцию. Атакующий называет жертву `owner`, а `destination` — свой кошелёк.
2. **Нет `has_one`.** Атакующий подписывает транзакцию сам, но передаёт ledger **жертвы**. Программа проверяет, что подписант есть, но не связывает его с ledger.
3. **Underflow.** `wrapping_sub` не падает при снятии больше баланса. Лишние лампорты выходят из **общего** пула, то есть из денег других пользователей. Баланс в ledger заворачивается к `u64::MAX`.
4. **Нет проверки владельца.** Конфигурация читается из `UncheckedAccount` вручную, дискриминатор проверяется, а программа-владелец нет. Атакующий создаёт аккаунт, **байт-в-байт похожий на `Config`** с собой в роли админа, но принадлежащий его программе, и сливает весь пул.
5. **Произвольный CPI.** Адрес «платёжной» программы приходит от вызывающего. Программа [`evil_program`](programs/evil_program/src/lib.rs) отвечает `Ok` на любую инструкцию и ничего не делает, но ledger атакующего уже увеличен. Обычный `withdraw` затем выплачивает эти «деньги» из пула. Это цепочка из двух шагов, частая в реальных взломах.

Тесты проверяют **конкретный код ошибки**, а не просто факт отказа: транзакция могла бы упасть по постороннему поводу, и тест всё равно прошёл бы. Тест `honest_flows_work...` подтверждает, что исправления не сломали обычную работу.

Поддельный `Config` в тесте 4 создаётся напрямую в LiteSVM (`set_account`): на реальной сети атакующий делает то же самое, развернув собственную программу, которая владеет таким аккаунтом.

## Чек-лист для аудита, который следует из лабы

- Каждый аккаунт с правами должен быть `Signer`, а не просто совпадать по ключу.
- Каждая связь между аккаунтами (`владелец ↔ запись`) закреплена `has_one` или seeds.
- Данные программы читаются через типизированный `Account<T>`: он проверяет владельца и дискриминатор.
- Любая арифметика с деньгами использует `checked_*`. В `Cargo.toml` включено `overflow-checks = true`.
- Адреса программ для CPI — `Program<T>`, а не `UncheckedAccount`.
- Исправление проверяется тестом: тот же эксплойт падает, обычный сценарий работает.

Roofic применяет эти правила в `roofic_shares` и `roofic_portfolio` (неделя 11): `has_one`, `Program<Token2022>`, `Program<RooficShares>`, `checked_*`.
